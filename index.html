Project Overview & General Questions
12 Questions
Q1Can you tell me about your project in simple words?▼

My project name is CoverMate. It is an insurance web app.

In this app, a user can do four main things. First, they can see and compare different insurance policies. Second, they get suggestions on which policy is best for them. Third, they can file a claim when something bad happens — like an accident. Fourth, they can check what is the current status of their claim.

There is also an admin side. The admin can see all claims and check if any claim looks fake or suspicious.

I built both the frontend — which is what the user sees on screen — and the backend — which is the part that stores data and runs all the logic.

Q2What technologies did you use and why?▼

React.js — I used this for the frontend. It helps me build web pages fast. Each page is made of small parts called components.

FastAPI (Python) — I used this for the backend. It is easy to write and it automatically creates a page where you can test all APIs. It is also very fast.

PostgreSQL — I used this as the database. It is a very popular database that stores data in tables like Excel sheets.

Google Drive API — The original plan was to use AWS S3 for storing files. But AWS needs a credit card and has a cost. Google Drive is free and works in a similar way. So I used Google Drive to store the documents that users upload with their claims.

Celery — I used this to send emails in the background. When a claim status changes, the user gets an email. Celery does this work quietly in the background so the app does not slow down.

JWT — I used this for login and security. It keeps track of who is logged in.

Q3What are the main parts of your project?▼

My project has five main parts:

Part 1 — Login and Profile: User can create an account, log in, and fill in their personal details like age, income, and health condition.

Part 2 — Policy List: User can see all available insurance policies and compare them with each other.

Part 3 — Recommendations: The app looks at the user's age, income, and health. Then it gives a score to each policy and shows the top 5 best policies for that user.

Part 4 — Claims: User can file a claim, upload documents as proof, and check the claim status anytime.

Part 5 — Admin and Fraud Check: The admin can see all claims. The app also checks automatically if a claim looks fake or suspicious.

Q4What was the hardest part of building this project?▼

The hardest part was connecting Google Drive to my project for file uploads.

Google Drive needs a special login process called OAuth2. The first time the app runs, it opens a browser and asks for Google permission. After that, it saves the login details in a file called token.pickle. Next time, it uses this saved file and does not ask again.

Understanding this whole process took me some time. I read the Google documentation carefully and tested it step by step. I also asked my mentor in the daily meeting and they helped me understand it better.

Q5How did you manage your work during the 8 weeks?▼

My mentor gave me a week-by-week plan at the start of the internship. Each week had a clear goal. So I always knew what I had to finish.

For example, in Week 1 and 2, I had to build the login and policy list. In Week 3 and 4, I had to build the recommendation system. In Week 5 and 6, the claims part. In Week 7 and 8, the fraud check and admin dashboard.

Every day we had a short meeting. In that meeting I said: what I finished yesterday, what I will do today, and if I have any problem. This helped me stay on track every day without getting confused.

Q6Is this a full stack project? What did you do in it?▼

Yes, this is a full stack project. That means I built both the frontend and the backend.

On the frontend side, I made all the web pages using React — like the login page, the policy page, the claims page, and the admin dashboard.

On the backend side, I built all the APIs using FastAPI. I also designed the database tables, set up Google Drive for file uploads, set up Celery for email notifications, and added the JWT login system.

It was an individual project. But whenever I was stuck, I asked my mentor and my team members for help in the daily meetings.

Q7What is a REST API? Is your project using it?▼

REST API is a way for the frontend and backend to talk to each other using the internet.

Think of it like this: the frontend is a customer and the backend is a waiter. The customer says "I want to see the menu" — that is a GET request. The customer says "I want to order this dish" — that is a POST request. The customer says "change my order" — that is a PUT request.

Yes, my project uses REST API. For example, when a user files a claim, the React page sends a POST request to the FastAPI backend. The backend saves the claim in the database and sends back a reply.

Q8What is CORS and why did you add it?▼

CORS means Cross-Origin Resource Sharing. It is a browser safety rule.

By default, a browser does not allow one website to talk to a different website. My React app runs on address localhost:3000 and my FastAPI backend runs on localhost:8000. These are two different addresses. So the browser blocks them from talking to each other.

To fix this, I added CORS settings in FastAPI. I said: "Please allow requests coming from localhost:3000." After this, the frontend and backend can communicate properly.

Q9What is the difference between frontend and backend?▼

Frontend is what the user sees and uses — the buttons, forms, and pages on the screen. I built this using React.js.

Backend is what runs behind the screen — the logic, the database, and the APIs. The user never sees it directly. I built this using FastAPI and Python.

Simple example: when a user clicks "File Claim," the frontend sends the claim details to the backend. The backend saves it in the database, checks for fraud, and sends back a reply. The frontend then shows a success message to the user.

Q10What types of insurance policies does your app support?▼

My app supports 5 types of insurance policies:

Auto — for vehicles like cars and bikes.

Health — for hospital bills and medical expenses.

Life — for family protection if something happens to the person.

Home — for house damage or theft.

Travel — for trips, in case of flight cancellation or luggage loss.

In the database, these five are stored as fixed allowed values. This makes sure no wrong value can be saved by mistake.

Q11How is your project different from a normal insurance website?▼

A normal insurance website just shows a list of policies. My project does more than that.

First, it has a recommendation engine. It looks at the user's age, income, number of family members, and health condition — and then suggests the best policies for that specific person.

Second, it has an automatic fraud detection system. When a claim is filed, the system checks if the claim looks suspicious — like if the amount is too high, or if the claim is filed too soon after buying the policy.

Third, users get an email notification whenever their claim status is updated. This is done automatically in the background.

These three things make it smarter than a basic insurance website.

Q12What would you add or improve if you had more time?▼

I would improve a few things:

First, right now the admin is checked by a hardcoded email id in the code. This is not a good practice. I would add a proper "role" for users — like admin or normal user — stored in the database.

Second, I would add a payment option so users can actually pay for a policy online using something like Razorpay.

Third, I would move to a proper cloud storage like AWS S3 or Firebase instead of Google Drive, because those are better for production use.

Fourth, I would write automated tests for the code so that when I change one thing, I can quickly check nothing else broke.

Fifth, I would deploy the app on a real server so anyone can use it from the internet.

Backend — FastAPI, Python & Logic
12 Questions
Q13Why did you choose FastAPI and not Flask or Django?▼

All three — FastAPI, Flask, and Django — are Python tools for building backends. But they are different.

Django is very big and has many built-in things. It is good for very large projects. For my project, it felt like too much.

Flask is smaller and simple. But it does not have many automatic features.

FastAPI is also small and simple like Flask, but it has one very useful feature — it automatically creates a testing page at /docs where I can test all my APIs directly in the browser. This saved me a lot of time during development. It is also very fast. That is why I chose FastAPI.

Q14What is a router in FastAPI? Why did you use it?▼

A router is a way to keep your code organized by splitting it into separate files.

In my project, instead of writing all the APIs in one big file, I made separate files for each feature. For example, claims.py has all claim-related APIs, admin.py has all admin APIs, policies.py has all policy APIs, and so on.

Each file has its own router. Then in main.py, I connect all these routers together. This makes the code clean and easy to find. If someone wants to change something in claims, they only go to claims.py — they do not have to search through one big file.

Q15What is Pydantic and why did you use schemas?▼

Pydantic is a tool that checks if the data the user sends is correct.

For example, when a user files a claim, they must send the claim amount, the type of claim, and the date of the incident. If they forget to send any of these, or if they send a wrong type — like sending a word where a number is expected — Pydantic will catch that error and send back a clear message saying what is wrong.

I created these rules in a file called schemas.py. I made one schema for creating a claim, one for signup, and so on. FastAPI automatically uses these schemas to check all incoming data.

Q16What is Celery? Why did you use it for emails?▼

Celery is a tool that runs tasks in the background — separately from the main app.

Here is the problem it solves. When an admin changes a claim status, the app needs to send an email to the user. Sending an email takes a few seconds. If I send it directly inside the API, the admin has to wait and see nothing happen for a few seconds. That feels slow and bad.

With Celery, I just say "please send this email" and the API immediately replies to the admin — done! Celery then sends the email quietly in the background. The admin does not have to wait at all. This makes the app feel fast.

Q17Can you explain how the fraud detection works in your project?▼

When a user files a claim, my app automatically runs 4 checks to see if the claim looks fake.

Check 1 — Big Amount: If the claimed amount is more than one lakh rupees, it is marked as high risk. Reason: very large amounts are suspicious.

Check 2 — Too Fast: If the claim is filed within 7 days of buying the policy, it is flagged. Reason: normally people do not have accidents on the very first week of buying insurance.

Check 3 — Same Amount Twice: If the same person already filed a claim for the same amount before, it is flagged. Reason: exact same amounts look copy-pasted.

Check 4 — Many Claims at Once: If the same person files 2 or more claims within just 3 days, it is flagged as high risk.

If a high-risk flag is found, the claim status is automatically changed to "under review" so the admin knows to look at it carefully. All these flags are saved in the database.

Q18How does the recommendation engine work?▼

The recommendation engine gives a score to each policy based on the user's details. The higher the score, the better the policy is for that user.

Here is how the score is calculated:

If the policy's cost (premium) is less than 5% of the user's yearly income — the user gets 25 points. This means the policy is affordable for them.

If the user is high risk (age above 50, or has 3 or more family members, or has a critical health condition) and the policy has a low deductible — they get 20 points. A low deductible means the user pays less from their own pocket when they make a claim.

If the user has 2 or more family members — they get 10 extra points because the policy should cover the whole family.

After scoring all policies, the top 5 are shown to the user with a reason like "Affordable based on your income."

Q19What is SQLAlchemy? How did you use it?▼

SQLAlchemy is a Python tool that helps you work with the database using Python code — instead of writing database language (SQL) directly.

In my project, I wrote Python classes in models.py to represent database tables. For example, the Claims class represents the claims table. Each column in the table is written as a Python variable.

Instead of writing INSERT INTO claims ... in SQL, I just write db.add(new_claim) in Python. SQLAlchemy handles the rest. This is easier to read and also safer — it protects from common attacks like SQL injection.

Q20What is dependency injection in FastAPI? Give a simple example.▼

Dependency injection means FastAPI automatically gives a function what it needs — without you having to write extra code.

Example 1 — Database connection: I write db: Session = Depends(get_db) in any API function. FastAPI will automatically open a database connection, pass it to my function, and close it when done. I do not have to open or close the connection myself.

Example 2 — Current user: I write current_user = Depends(get_current_user). FastAPI automatically reads the login token from the request, checks who it belongs to, and gives me the user object. I do not have to do this check in every single API myself.

It saves a lot of repeated code and keeps things clean.

Q21What does db.commit() and db.rollback() do?▼

Think of the database like a notebook. When you write something, it is first written in pencil (not saved yet).

db.commit() is like pressing "Save." It makes the changes permanent in the database.

db.rollback() is like pressing "Undo." It cancels all the changes that were not saved yet.

In my file upload code, if something goes wrong during the upload — for example the Google Drive upload fails — I call db.rollback(). This means no broken or incomplete data gets saved in the database. The database stays clean and correct.

Q22How did you send emails in your project?▼

I used Python's built-in smtplib library to send emails through Gmail.

When the admin changes a claim's status, a Celery background task runs. This task does the following steps:

Step 1 — It finds the claim in the database using the claim ID.

Step 2 — It finds which user made that claim.

Step 3 — It gets the user's email address.

Step 4 — It creates an email saying "Your claim status has changed to [new status]."

Step 5 — It connects to Gmail's server and sends the email.

I used a Gmail App Password — which is a special password just for apps — instead of my real Gmail password. This is a safer way to do it.

Q23What is an error response in FastAPI? How did you handle errors?▼

When something goes wrong in my API, I use HTTPException to send back an error message to the frontend.

For example, if a user tries to file a claim for a policy that does not belong to them, I send back a 403 error with the message "Invalid user policy." The frontend can then show this message to the user.

I used different error codes for different situations. 404 means "not found" — for example when a claim ID does not exist. 403 means "not allowed" — when the user is trying to do something they should not. 500 means something broke on the server side.

Q24What is the difference between GET, POST, and PUT?▼

These are the three main ways the frontend sends requests to the backend.

GET — used to read or fetch data. Nothing is changed. Example: "Show me all my claims." The frontend sends a GET request to /claims/.

POST — used to create something new. Example: "I want to file a new claim." The frontend sends a POST request with the claim details.

PUT — used to update something that already exists. Example: "Change this claim's status to approved." The admin sends a PUT request to /claims/{id}/status.

In REST API rules, we always use the right method for the right action. We do not use GET for creating data or POST for updating data.

Database — PostgreSQL & Tables
10 Questions
Q25How many tables are in your database? Can you explain each one?▼

My database has 8 tables. Let me explain each one simply:

Users — stores the user's name, email, password, date of birth, and their risk profile details.

Providers — stores the insurance company details like name and country.

Policies — stores each insurance policy — its type, cost (premium), coverage details, and deductible amount.

UserPolicies — records which user bought which policy, with start date, end date, and status (active or expired).

Claims — stores each claim filed by a user — the amount, date of incident, and current status.

ClaimDocuments — stores the Google Drive link of documents the user uploaded for their claim.

Recommendations — stores the score and reason for each policy that was recommended to each user.

FraudFlags — stores which fraud rule was broken for each suspicious claim.

AdminLogs — records what actions the admin has taken.

Q26What is a foreign key? Give an example from your project.▼

A foreign key is a column in one table that points to a row in another table. It creates a connection between two tables.

Simple example: Think of two books. Book 1 is the Students list. Book 2 is the Marks list. Every row in the Marks list has a Student ID that points to a student in the Students list. That Student ID is a foreign key.

In my project: The Claims table has a column called user_policy_id. This column points to the UserPolicies table. So every claim is connected to one specific user policy. You cannot file a claim without a valid policy linked to it.

Q27What is JSONB in PostgreSQL? Why did you store some data in it?▼

JSONB is a special type of column in PostgreSQL where you can store flexible data that looks like a dictionary or a list. It is like storing a small JSON file inside a database column.

I used it in two places:

risk_profile in Users table — each user has different details. One user might have age, income, and dependents. Another might also have a health condition. These fields are not the same for everyone. So I stored it as JSONB instead of making many fixed columns.

coverage in Policies table — different types of policies cover different things. A health policy covers hospital bills. A travel policy covers flight cancellation. The details are different each time. So JSONB is a good fit here.

Q28What is the difference between primary key and unique key?▼

Both primary key and unique key make sure no two rows have the same value. But they are a little different.

Primary Key — every table must have exactly one. It is the main way to identify a row. It cannot be empty. In all my tables, the column id is the primary key — it is a number that goes up automatically (1, 2, 3, ...).

Unique Key — it also stops duplicates, but a table can have many unique keys. It can sometimes be empty (NULL). Example: In my Users table, the email column is unique. No two users can have the same email. In my Claims table, the claim_number is unique — no two claims can have the same number.

Q29What is CASCADE delete? Where did you use it?▼

CASCADE delete means: when you delete a parent record, all the child records linked to it are automatically deleted too.

Simple example: if you delete a student from the Students table, their marks in the Marks table should also be deleted automatically. Otherwise, you will have marks records with no student — which is confusing and useless data.

In my project, I used this in the Claims table. The user_policy_id column has ondelete="CASCADE". So if a user policy is deleted, all claims linked to that policy are also automatically deleted. I used it in several other places too — like deleting claim documents when a claim is deleted.

Q30What is an ORM? Why is it better than writing SQL directly?▼

ORM stands for Object Relational Mapping. It is a tool that lets you use your programming language — in my case Python — to talk to the database. You do not have to write SQL commands directly.

I used SQLAlchemy as my ORM.

Why is it better? Three reasons:

First, it is easier to read. Python code is cleaner than SQL mixed into Python strings.

Second, it is safer. When you write SQL as a plain string and put user input inside it, hackers can change the query. ORM protects from this type of attack automatically.

Third, it works with different databases. If I want to switch from PostgreSQL to MySQL, I change very little code — the ORM handles the difference.

Q31What is a JOIN? Did you use it in your project?▼

A JOIN is a way to combine data from two tables at the same time when they are connected.

Simple example: if you want to find a student's marks along with their name, you JOIN the Students table and the Marks table using the student ID.

Yes, I used it in my project. To get all claims for the current user, I write:

db.query(Claims).join(UserPolicies).filter(UserPolicies.user_id == current_user.id)

The Claims table does not have the user_id directly. It only has user_policy_id. So I JOIN the UserPolicies table to get the user_id from there. Then I filter to show only the current user's claims.

Q32Why did you use server_default=func.now() for timestamps?▼

This means: when a new row is saved in the database, the database server automatically fills in the current date and time — I do not have to send it from Python.

Why is this better than using Python's time? Because the database server's clock is more accurate and consistent. If your app runs on multiple servers, their clocks might be slightly different. Using the database server's own clock makes sure all records have a consistent, correct timestamp.

I used this for the created_at column in tables like Claims, ClaimDocuments, and FraudFlags.

Q33Why did you use NUMERIC instead of a normal number type for money?▼

For money, we need exact decimal values. For example, a premium might be ₹5,250.75 — not ₹5,250 or ₹5,251.

If I use a regular float type (like float in Python), the computer sometimes stores it as ₹5,250.7499999 because of how computers handle decimal numbers. This small difference can cause big problems when you are adding up money for thousands of users.

NUMERIC(12, 2) stores the exact number — up to 12 digits total and exactly 2 decimal places. This is the standard and safe way to store money values in any database.

Q34What is the Recommendations table? How is it used?▼

The Recommendations table stores the result of the recommendation engine for each user.

Every time a user asks for recommendations, my code goes through all policies, calculates a score for each one, and saves the score and reason in this table — linked to the user's ID and the policy's ID.

Before saving new recommendations, I first delete the old ones. This keeps the data fresh and updated every time.

The top 5 policies by score are then sent back to the user's screen. The admin can also later check what was recommended to each user by looking at this table.

Login & Security — JWT & Passwords
8 Questions
Q35What is JWT? Explain in simple words how it works in your project.▼

JWT stands for JSON Web Token. It is a way to verify who the user is — without storing their login information on the server every time.

Think of it like an entry pass to a concert. When you buy a ticket, you get a pass. At the gate, they check the pass — they do not need to call the ticket office every time. The pass itself proves you are allowed in.

In my project it works like this:

Step 1 — The user enters their email and password in the login page.

Step 2 — The backend checks if the email and password are correct. If yes, it creates a JWT token and sends it to the frontend.

Step 3 — The frontend saves this token. Every time it sends a request to the backend, it includes this token.

Step 4 — The backend reads the token, checks it is valid, and knows who the user is — without checking the database again.

Q36What are the three parts of a JWT token?▼

A JWT token looks like this: xxxxx.yyyyy.zzzzz — three parts separated by dots.

Part 1 — Header: Tells what algorithm is used to create the token. In my project I used HS256.

Part 2 — Payload: Contains the user's information — like their email and when the token expires. This part is readable by anyone who has the token, but it cannot be changed without being caught.

Part 3 — Signature: This is the security part. It is created by combining part 1 and part 2 with a secret key that only my server knows. If someone tries to change anything in the token, the signature will not match and the token becomes invalid.

Q37How did you save passwords safely? Why is it important?▼

I never saved the real password in the database. Instead, I saved a hashed version of the password.

Hashing means the password goes through a process that converts it into a long random-looking string. For example, the password "hello123" becomes something like "x9q$2mK#r...". This cannot be reversed — you cannot get back "hello123" from that string.

I used a library called bcrypt for this. It is a very safe and popular way to hash passwords.

Why is this important? If someone hacks the database, they only see the hashed strings — not the real passwords. Even I cannot read the users' passwords. When a user logs in, I hash what they typed and compare it with the stored hash. If they match, the login is allowed.

Q38When does the JWT token expire? What happens after that?▼

In my project, the JWT token expires after 30 minutes. I set this in the code as ACCESS_TOKEN_EXPIRE_MINUTES = 30.

After 30 minutes, if the user tries to do anything — like view their claims — the backend will reject the request. It will send back a 401 error which means "not logged in."

At that point, the user needs to log in again to get a new token.

In a real production app, we would also add something called a refresh token. This is a second token that lasts longer (like 7 days) and can be used to get a new access token automatically — so the user does not have to keep logging in again and again. I did not build this part yet, but I know it is the next step.

Q39What is OAuth2? How did you use it in this project?▼

OAuth2 is a way to allow one app to access another app on your behalf — without sharing your password.

I used OAuth2 in two places in my project:

For user login: FastAPI has a built-in tool called OAuth2PasswordBearer. It reads the token from the request header and passes it to my code so I can check who is logged in.

For Google Drive: To upload files to Google Drive, my app needs permission from Google. OAuth2 is how Google gives that permission. The first time, a browser window opens and asks the user to allow access. After the user says yes, Google gives a credential that my app saves to a file and uses for future uploads — without asking again every time.

Q40How did you handle admin access in your project?▼

I made a special function called admin_only in the admin file. This function checks: is the currently logged-in user's email the same as the admin's email?

If yes — the request is allowed. If no — it sends back a 403 error saying "Admin access required."

All admin routes — like seeing all claims or exporting the CSV — use this admin_only check. So a normal user cannot access those pages even if they try.

I know this method is simple and not ideal for a big app. In a real app, I would store a "role" column in the database — like "admin" or "user" — and check that instead of checking a hardcoded email.

Q41What is the difference between authentication and authorization?▼

These two words sound similar but mean different things.

Authentication means checking who you are. Example: when you enter your email and password to log in, the system checks if you are a registered user. This is authentication. After this you get a JWT token.

Authorization means checking what you are allowed to do. Example: even though you are logged in, you cannot open the admin dashboard. Only the admin user is allowed to do that. This check is authorization.

Easy way to remember: Authentication = "Are you who you say you are?" Authorization = "Are you allowed to do this?"

Q42Are there any security problems in your project? Can you be honest about it?▼

Yes, I can honestly say there are a few things that need improvement for a real production app.

First, the secret key used for JWT is written directly in the code as a simple word. In a real app, this should be a long random value stored in a separate environment file, not in the code.

Second, the Gmail password used for sending emails is also written directly in the code. This is not safe if the code is shared publicly. It should also be in a separate environment file.

Third, the admin is identified by a hardcoded email. In a real app, there should be a proper role system in the database.

Fourth, uploaded files on Google Drive are made public — anyone with the link can see them. For sensitive insurance documents, this is a problem. A better approach would be to keep them private and generate temporary links.

I know these issues because I was building and learning at the same time. These are good lessons for my next project.

Google Drive API & File Uploads
6 Questions
Q43Why did you use Google Drive instead of AWS S3?▼

The original plan in the project document mentioned using AWS S3 for storing uploaded files. But AWS S3 needs a credit card and has costs, even though there is a free tier. For an internship project, it was not practical.

Google Drive API is completely free with a Google account and gives 15 GB of storage. The main goal of this module was to learn how to upload files to a cloud storage and store the link in the database. Google Drive achieves that goal perfectly.

The logic is almost the same — upload the file, get a shareable link, save the link in the database. I also learned how Google's API and OAuth2 permission system works, which is a valuable skill.

Q44Can you explain step by step what happens when a user uploads a document?▼

Here is what happens step by step when a user uploads a claim document:

Step 1: The user selects a file on the React page and clicks the upload button.

Step 2: The React page sends this file to the backend at the address /claims/{claim_id}/upload.

Step 3: FastAPI receives the file. It first checks if this claim belongs to the current user. If not, it returns an error.

Step 4: The file is saved as a temporary file on the server — for example temp_document.pdf.

Step 5: My code calls the Google Drive function. It uploads the temp file to a specific Google Drive folder.

Step 6: Google Drive gives back a file ID. My code makes the file public and creates a shareable link like https://drive.google.com/file/d/....

Step 7: This link is saved in the ClaimDocuments table in the database.

Step 8: The temp file on the server is deleted — always, even if something went wrong.

Step 9: The link is sent back to the React page as the response.

Q45What is token.pickle? Why is it used?▼

token.pickle is a file that stores the Google login credentials after the first time the app connects to Google.

The first time my app runs and tries to use Google Drive, it opens a browser window and asks for permission — "Do you allow this app to access your Google Drive?" After you click Allow, Google gives a set of credentials (like a login pass). My code saves these credentials to a file called token.pickle.

The next time the app runs, it reads from this file instead of opening the browser again. If the credentials have expired, it automatically refreshes them in the background without any browser popup.

This makes the app easier to use — the user only has to click Allow once.

Q46What is the finally block in your upload code? Why is it important?▼

The finally block is a part of the code that runs no matter what — whether the upload worked perfectly or something went wrong.

In my upload code, after the file is received from the user, I save it temporarily on the server. I need to do this because Google Drive's upload function needs a file path — it cannot read directly from memory.

After the upload to Google Drive is done — or if it fails — I always want to delete this temporary file. If I do not delete it, the server keeps collecting these files and runs out of space over time.

So in the finally block I check: if the temp file exists, delete it. This cleanup always happens — success or failure. That is the purpose of finally.

Q47What Google Drive permission (scope) did you use? What does it mean?▼

I used the scope https://www.googleapis.com/auth/drive.file.

In simple words, this scope means: my app can only see and manage the files that it uploaded itself. It cannot see or touch any other files in the user's personal Google Drive.

This is important for safety. If I had used a full access scope, my app would be able to read all the user's personal files — emails, photos, documents — which is a big privacy risk.

By using the smallest permission that my app needs, I follow a rule called "least privilege" — only ask for what you actually need, nothing more.

Q48What does resumable=True mean in your file upload code?▼

When I upload a file to Google Drive, I use MediaFileUpload(file_path, resumable=True).

Resumable means: if the internet connection breaks in the middle of an upload, the upload can continue from where it stopped — instead of starting from zero again.

For example, if a user uploads a large PDF file and the internet cuts off at 60%, a resumable upload will continue from 60% when the connection comes back. Without resumable, it would have to start all over from 0%.

For claim documents — which can be scanned PDFs and are sometimes large — this makes the upload more reliable.

Q50What is React Router? How did you use it?▼

React Router is a tool that helps the user move between pages in a React app without reloading the whole browser every time.

Normally, when you click a link on a website, the browser downloads a completely new page. This takes time and the screen flashes.

With React Router, all the pages are already loaded in the background. When you click a link, React just shows the correct page component — no full reload. This makes the app feel very fast and smooth, like a mobile app.

In my App.js, I defined all the routes — like /login shows the Login page, /policies shows the Policies page, /claims shows the My Claims page, and so on.

Q51How does the frontend send requests to the backend?▼

The frontend uses HTTP requests to talk to the backend. I used the browser's built-in fetch function for this.

For example, when a user opens the My Claims page, React calls fetch("http://localhost:8000/claims/"). But before sending, it adds the JWT token to the request header like a key card — so the backend knows who is asking.

The backend receives the request, finds the claims for that user in the database, and sends back the list. React then shows that list on the screen.

This is how every page works — the frontend asks, the backend answers, the frontend displays.

Q52What is the difference between state and props in React?▼

Both state and props store data in React, but they work differently.

State is data that belongs to a component and can change. When state changes, the screen updates automatically. Example: when the My Claims page loads, I fetch the list of claims from the backend and save it in state. When the list arrives, the screen shows the claims without needing a page refresh.

Props is data that a parent component gives to a child component. The child cannot change it — it can only read it. Example: if I have a ClaimCard component, I pass the claim details to it as props. The card just displays whatever it receives.

Simple way to remember: State is your own data. Props is data given to you by someone else.

Q53What is useEffect in React? Where did you use it?▼

useEffect is a React hook — a special function — that runs some code when the page first loads or when something specific changes.

I used it to fetch data from the backend when a page opens.

For example, in the Policies page, I wrote a useEffect that calls the FastAPI GET /policies API as soon as the page loads. The result (list of policies) is saved in state. React then shows all the policies on the screen automatically.

Without useEffect, the page would load empty and nothing would appear — because React would not know when to go and fetch the data.

Q54What does the Admin Dashboard show? How does it work?▼

The Admin Dashboard is a special page that only the admin can see.

When the admin opens it, the page automatically calls the backend and loads:

Summary numbers — total number of users, total claims, total policies sold, total fraud flags found, total premium collected, and total amount claimed.

All claims list — each claim is shown with its documents and any fraud flags it has.

Status update — the admin can click on a claim and change its status to "approved," "rejected," or "paid." When they do, the user gets an email automatically through Celery.

Export button — the admin can download all claims as a CSV file (like an Excel sheet) to keep a record or analyze offline.

Q55What is a component in React? Explain simply.▼

A component is a small, separate piece of a web page. Think of a web page like a house made of Lego blocks. Each block is a component.

For example, the Login page in my project is one component. The Policies page is another component. Inside the Policies page, there might be a smaller component for each policy card.

Each component has its own code, its own data (state), and its own look (HTML and CSS). We build big pages by putting smaller components together.

The benefit is reuse. If I build a PolicyCard component, I can use it on the Policies page, the Compare page, and the Recommendations page — without writing the same code three times.
